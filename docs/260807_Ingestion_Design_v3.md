## 三、正确的数据源

产品定义写的是 analyze store flyers。所以正确来源是**门店传单**，不是商品库。

```
GET https://www.99ranch.com/be-api/store/web/viewAd?storeId={门店ID}
请求头：storeid: {门店ID}          ← 唯一必需的头
```

返回若干个 activity（板块），每个板块 = 传单的一页：

```json
{"id": 12991, "name": "Unbeatable Deals", "date": "Aug.07 - Aug.13",
 "imageUrl": "https://img.awsprod.99ranch.com/xxx.jpeg", "imageText": "{}"}
```

**湾区 16 家门店返回完全相同的一套页** —— 一份传单覆盖整个北加州。只需抓一次，不是 16 次。

湾区门店 ID：

```
1688 1701 1702 1761 1762 1766 1768 1769
1771 1772 1773 1775 1779 1781 1782 1783
```

（1772 = Mountain View）

### 本周（08/07–08/13）的构成

共 **21 页**：

```
p00–p08   常规促销
          Unbeatable Deals / Weekend Special / Monthly Value Picks /
          Perishables / Dry Grocery / Beverages·Snack·Frozen /

p09–p19   月饼专题 ×11
```

约 291 格，其中约 60 格是生鲜/冷藏/冷冻 —— 正是我们最需要、而仓库渠道一件都没有的那部分。

## 四、传单只有图，没有文字来源（排除法结论，别再查一遍）

`imageText` 字段**在所有门店的所有页上都是字符串 `"{}"`**。这是零售商从没填过的一个槽位，不是我们请求方式不对。

其它路都走过了：

| 试过的路 | 结果 |
|---|---|
| Flipp（我们已在用的聚合平台） | **不收 99 Ranch**。4 个湾区邮编都查过 |
| 第三方传单聚合站 | 有 99 Ranch，但全是**南加州版** —— 跟仓库一样的坑，换个形式 |
| 99 Ranch 手机 App | 走同一批 JPEG，没有额外接口 |
| 图片的 PDF / JSON 变体 | 不存在，只有 `.jpeg` |
| 商品库接口 + 传单对齐 | 商品库价格和传单价格会打架，见第十一节 |

**结论：想拿到北加州传单的内容，只能读图。** 这是穷尽之后的结论，不是没找够。

## 五、覆盖范围（2026-08-07 实测）

### 5.1 共用关系

**重测方法**：对每个邮编调 `GET https://backflipp.wishabi.com/flipp/data?postal_code={邮编}&locale=en-us`，
把返回的 flyer 按 `merchant` 筛出，再按 `flyer_id` 分组。99 Ranch 不在 Flipp 上，单独调 `viewAd`。

实测 16 个湾区邮编：

| 传单区 | flyer_id | 覆盖邮编数 | 覆盖哪些 |
|---|---|---|---|
| **Safeway-A** | 8059566 | 12 | 94132 SF-西、94010 Burlingame、94301 Palo Alto、94040 Mountain View、94086 Sunnyvale、95128 San Jose、95035 Milpitas、94538 Fremont、94566 Pleasanton、94588 Dublin、94550 Livermore、94061 Redwood City |
| **Safeway-B** | 8059567 | 4 | 94102 SF-市中心、94112 SF-南、94601 Oakland、94706 Albany |
| **Cardenas-A** | 8061499 | 16 | 全部 16 个 |
| **H Mart-A** | 8070588 | **4** | 94040 Mountain View、94086 Sunnyvale、95128 San Jose、95035 Milpitas |
| **99 Ranch-北加** | 21 个板块 id | 不按邮编 | 湾区 16 家门店共用同一套 |

### 5.2 三件要记住的事实

**① Safeway 在湾区内部分两区，差异约 1%。**
两份各 214 件，商品名重合 211 件，各有 3 件独有。共同商品里价格不同的只有 2 件：

```
Pepsi     Safeway-A $2.49   Safeway-B $2.99
Monster   Safeway-A $1.99   Safeway-B $2.29
```

差异真实存在但很小 —— 跟 99 Ranch 那次 5/5 全错完全不是一个量级。

**② H Mart 只覆盖南湾 4 个邮编。** 旧金山和东湾**根本没有 H Mart 传单**。这是服务范围的硬边界，不是抓取失败。

**③ 匹配商家必须用精确名，不能用子串。**
研究过程中曾把 `Health Mart Pharmacy`（药房连锁，id 8052713，月度传单，32 件全是 Claritin/Crest/Excedrin）误判成 H Mart 的第二份传单 —— 因为 `"health mart pharmacy"` 里含子串 `"h mart"`。

生产代码没有这个 bug（`stores.py` 配的是精确名 `"H Mart"`）。但这正是 `FieldAudit_v1` 第一节那条方法论的又一次应验：**「同一回事」必须比数值/比精确标识，不能看名字。**

> 当时还有一个本该触发警觉的信号：那两份传单**零重合**。同一家超市的两份传单不可能一件都不重复。异常干净的数据要当成警报，不是当成好消息。

### 5.3 命名与服务范围声明

门店的单位是 **商家 + 传单区**，不是商家 + 邮编 —— 否则 Cardenas 一份传单会变成 16 家「店」持有同一份数据。

```
Safeway-A / Safeway-B / Cardenas-A / H Mart-A / 99 Ranch-北加
```

另配一张 **邮编 → 传单区** 的映射表，用户按自己的邮编查到该看哪个区。

**服务范围声明**（哪些商家 × 哪些传单区 × 哪些邮编在范围内）是每日对账的基准 —— 没有它，系统无法判断「该有什么」。

- **数据**放在 `Granny code/regions.py`（流水线每天要读）
- **决定与方法**放在本文（上面 5.1、5.2）

两份会随时间漂移。本文这份标注了实测日期和重测方法，**代码里的值与本文不一致时，那是「分区变了、该重测」的信息，不是错误**。

### 5.4 本版不抓的（显式决定，不是遗漏）

| 不抓什么 | 理由 |
|---|---|
| **Safeway-B（旧金山区）** | 与 Safeway-A 差异约 1%（2/211 价格）。等用户分布明确后再决定 |
| **99 Ranch 的 11 页月饼专题** | 季节性专题，怎么标注、要不要进主流程都没定 |

两条都不是「做不到」，是「先不做」。要抓的时候回来改这一节。

## 六、一店多批次

### 6.1 现在的约束

```sql
CREATE UNIQUE INDEX idx_one_published ON batches(store_name) WHERE status = 'published';
```

**一家店只能有一个已发布批次。** 这个约束当初解决的是「哪个批次是这家店的真相」——8 月 4 号之前，一个空批次会因为「按时间取最新」而反复抢回发布位。

### 6.2 为什么要改

Safeway 有两个传单区，99 Ranch 一份周传单由 21 个板块组成。一店一批次表达不了。

### 6.3 改成什么

```
UNIQUE(store_name, 传单区)  WHERE status = 'published'
```

仍然保证「任一（商家 × 传单区）只有一个真相」，但一家商家可以有多个批次同时在线。

**为什么不能只用「今天在有效期内」判定**：Safeway-A 和 Safeway-B 有 211 件重合商品、2 件价格不同。两份同时在线而没有区的概念，数据库里 Pepsi 就有两个价格，谁也说不清哪个对。**范围字段不落地，多批次就不能安全打开。**

### 6.4 batches 表要加的字段

| 字段 | 用途 |
|---|---|
| 传单区 | `Safeway-A` / `99 Ranch-北加` |
| 上游标识 | Flipp 存 `flyer_id`；99 Ranch 存板块 id 列表 |
| 抓取邮编 | 用哪个邮编取到的（可追溯）|
| 上游指纹 | 99 Ranch 存每页 ETag；Flipp 存件数 |

字段的具体定义归 `FieldSet`（源上有什么归 `FieldAudit`），这里只登记「因为多批次，需要这几样」。

## 七、每天对账

### 7.1 模型换了

| | 问的问题 | 看的对象 |
|---|---|---|
| 旧（`already_current()`） | 我有没有数据？没有就去抓 | **只看自己** |
| 新（对账） | 上游现在有哪几份？我有哪几份？对得上吗 | **两边比** |

只看自己，有一整类问题结构性地看不见 —— **「我不知道自己不知道」**：

| 场景 | 旧模型 | 对账 |
|---|---|---|
| **99 Ranch 抓的是仓库不是门店** | **四个月没发现。有数据、在有效期内、检查全过** | 上游湾区门店是 16 个 ID，我对的 8899 不在名单里 → **第一天就不一致** |
| 上游新增一份传单 | 永远发现不了 | 上游 N 份我有 N-1 份 → 不一致 |
| 上游换了传单但我的还没过期 | 跳过，继续供旧价 | 上游标识变了 → 不一致 |

**那次花了四个月的错误，对账第一天就能抓到；旧模型永远抓不到。** 这一条就足够说明该换。

### 7.2 比什么 —— 只比上游给的标识，绝不比我们解析出来的内容

| 源 | 比什么 | 成本 |
|---|---|---|
| **Flipp** | `flyer_id` + 有效期 + 件数 | 每个邮编 1 次请求拿传单列表；件数再 1 次 |
| **99 Ranch** | 板块 id + 日期 + **ETag** | 1 次 `viewAd` + 每页 1 次 **HEAD** 请求 |

**关键：99 Ranch 不需要下载图片，更不需要读图。**

实测 `HEAD` 请求返回：

```
ETag: "dc7148e91b10ae4b16d41620f8a3bfe2"
Last-Modified: Thu, 06 Aug 2026 20:43:34 GMT
Content-Length: 1023663
```

而这个 ETag **正好等于该文件的 MD5**（三页三个全部对上）。所以 21 次 HEAD 请求、总共几 KB，就能确定每一页有没有换过。

> **MD5 是什么**：文件的指纹。把任意大小的文件压成一串 32 位字符，文件里改一个像素这串字符就完全变样。用途是「判断两个文件是不是同一个」而不用真的传输文件。
>
> 注意：图片 URL 里那串 32 位十六进制**不是**内容哈希（实测与文件 MD5 对不上，那是上传 ID）。指纹要从 ETag 拿。

**只有指纹变了，才触发读图。** 下载 ≠ 读图：下载是流量，读图才花钱。

### 7.3 五类不一致，各配动作

| 形态 | 动作 |
|---|---|
| 上游有、我们没有 | 去抓 |
| 上游换了新标识（flyer_id / 板块 id / ETag 变了）| 去抓，旧的下线 |
| 上游出现一份我们从没见过的类型 | **告警给人** —— 这是新覆盖，要人决定抓不抓 |
| 我们有、上游没有了 | 下线，不删历史 |
| 我们的过期了、上游也没新的 | 告警，别装作有数据 |

### 7.4 兜底告警

**服务范围内的任一传单区，一份在有效期内的传单都没有 → 立即告警。**

这条比对账弱（对账能发现「少了一份」，这条只能发现「一份都没有」），所以它是兜底，不是主规则。

### 7.5 对账替代了旧模型的四道检查

旧的 `already_current()` 问四个问题，全部通过才跳过：

| 旧检查 | 在新模型里 |
|---|---|
| 有已发布数据盖住今天且真的有行 | 对账覆盖（且更强：还比上游标识）|
| 没有更新的失败记录 | 对账覆盖（按上游现实判断，不按我们的失败日志）|
| 今天已经真跑过一次 | **保留**，作为抓取的天花板 |
| 距上次真抓超过 8 天 | 不再需要 —— 对账每天跑，不存在「因为有效期长而整月不看」 |

## 八、触发方式

### 8.1 现在的问题

`com.remi.pipeline.plist` 同时开了两个触发器：

```xml
<key>RunAtLoad</key><true/>                      ← 每次登录/唤醒
<key>StartCalendarInterval</key> 06:00           ← 每天一次
```

`RunAtLoad` 的问题不是费电，是**触发次数不可预测** —— 取决于当天开合几次笔记本。一个不可预测的触发器，逼得代码里必须写闸门去兜底。

实测记录（改成每天之后）：

```
08-05  06:00 / 06:02 / 06:05     一次触发，四家店依次跑
08-06  06:00                      skip × 4
08-07  06:07                      99 Ranch 抓取 + skip × 3
```

更早（每周四时期）出现过同一天两个时刻（`07-16 06:01 和 07:23`），第二次大概率就是 `RunAtLoad`。

### 8.2 改成

```xml
删掉 RunAtLoad
StartCalendarInterval  06:00
StartCalendarInterval  13:00
```

一天两次固定机会，**次数有上限、可预测**。早上关机就下午补；两次都关机才丢一天 —— 传单按周换，丢一天下一天补回来。

### 8.3 为什么可以这么改

因为对账和抓取分开了：

```
对账   Flipp 每个邮编 1 次 + 99 Ranch 1 次 viewAd + 21 次 HEAD   ≈ 几十次请求，几 KB
抓取   每份传单约 200 次请求
```

**差约一百倍。** 对账便宜到多跑几次无所谓；抓取由对账结果触发，不由日程触发。

## 十、验证过的提示词

这段提示词读出了上面 87 条中的 62 条（p07 那 30 条 + Haiku 对照）。**它同时就是字段定义** —— 所以「定统一字段」必须先于「改抓取」，改了字段就是改提示词。

```
这是 99 Ranch Market 一周传单中的一页。逐格读出上面印的内容。

对每一个有价格的商品格，返回一个对象：
- codes: 印在格子左上角的 7 位商品编码，字符串数组。没印就空数组
- sizes: 印出来的规格，字符串数组，照原样抄（例如 "12x12oz"、"2x3.5oz"、"1 Liter"）。没印就空数组
- name_en: 英文商品名，照原样抄
- name_zh: 中文商品名，照原样抄。没有就 null
- price: 价格数字（例如 11.99）
- price_unit: 价格后面跟的单位，照原样抄，包括复合的（"EA"、"PK"、"PK+TX+CRV"、"EA + TAX"）
- multibuy: 如果印的是「N FOR $X」或「N PACKS $X」这类，填 N；否则 null
- conditions: 格子里印的其它条件文字（"MUST BUY 4"、"MIX & MATCH"、"Limit 4 items." 等），字符串数组

规则：
- 只抄图上印的，不要推断、不要补全、不要用你对这些商品的了解去填空
- 价格是拼出来的字形：$ + 大号整数 + 上标小号分币。11 加上标 99 就是 11.99
- 一个格子可能挂多个编码和多个规格，全部抄下来，不要配对
- 看不清就在该字段填 null，不要猜

只返回一个 JSON 数组，不要任何其它文字。
```

### 每条规则的来历

| 规则 | 为什么在 |
|---|---|
| **不要推断、不要补全** | 唯一那条真错就是违反了这条（把 5 个口味归纳成 "5 FLAVORS"）。模型对这些商品有先验知识，会拿知识补图上没印的东西 |
| **价格是拼出来的字形** | 传单价格是 `$` + 大号整数 + 上标小号分币三块拼的，不写清楚会读成 `$11` 或 `$1199` |
| **多编码多规格全抄不配对** | 一格挂 9 个编码却只印 3 个规格，**对应关系传单上根本没印**。让模型配对就是让它编 |
| **不让模型算单价** | 算术交给代码。模型只负责「图上印的是什么」，这样错了能一眼看出是读错还是算错 |
| **看不清填 null 不要猜** | null 是可检测的，猜出来的值不可检测 |

### 调用注意

`max_tokens=16000` 的非流式请求会撞 HTTP 超时、被对端关连接。必须用流式：

```python
with client.messages.stream(model="claude-sonnet-5", max_tokens=16000, …) as stream:
    resp = stream.get_final_message()
```
