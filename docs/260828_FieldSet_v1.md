## 四、定这些字段时用的规则

**1. 照抄层不做判断。** 归类、换算、判断两个规格是否等价，全是解析层的事。
模型只负责「图上印的是什么」——这样错了能一眼看出是**读错**还是**算错**。

**2. 位置只是提示，判据是「属不属于这一格」。** ← 最大的教训

前六轮把位置写成了字段定义（「格子左上角文字块里的规格」「粉色价签上的价格」），
结果 p01 有三条规格印在价签旁边就没被认出，落进了 `unmapped`。

而且末尾那条全局豁免（「上面任何字段举的例子都只是常见写法，不是白名单」）**救不了它**——
位置不是写成「例子」，是写成事实陈述的。

现在所有位置一律降级成「常见位置……，不限于这些」，防跨格的判据从
「同一个文字块」改成「跟这一格的商品名、价签在同一个框内」。

**3. 合并多种写法时，选覆盖面最大的那种形态。**

`sizes` 存字符串数组而不是「数值 + 单位」，因为八种形态里结构化只装得下一种。
不是「拼不回去」，是**拆的时候就装不进去**，事后无从补。

**4. 例子一律带「等等」，不是白名单。**

实证：`freshness` 的例子里没有 `LIVE`，`size_grade` 的例子里没有 `600G & UP`，
两个都靠「等等」接住了。写死枚举它们会变成 `null` 然后静默消失。

**5. 空值约定。**

```
数组字段  codes / sizes / surcharges / conditions / unmapped /
          page_raw_text / section_titles / page_unmapped      →  一律 []
标量字段  name_zh / sold_by / original_price / original_price_sold_by /
          multibuy / size_grade / freshness / section /
          valid_from / valid_to                                →  一律 null
```

**6. 允许跨字段重复，但字段和 `unmapped` 不能同时有。**

`raw_text` 里的每一段都必须能在某个字段或 `unmapped` 里找到。
多件写法同时进 `multibuy` 和 `conditions` 是**故意的**（见第六节）。

## 五、三个机制，以及它们为什么在

### `raw_text` —— 让空的 `unmapped` 变成可核对的断言

没有 `raw_text` 时，`unmapped: []` 有两种解释：「确实没剩下」和「模型没去看」，**分不出来**。

加了之后能用代码双向对账：

```
正向  字段里的值 → 能不能在 raw_text 里找到      查有没有凭空生成
反向  raw_text 的每一段 → 有没有落进某个字段     查有没有静默丢失
```

它也是**分步走的前提**：将来发现少个字段，从存好的 `raw_text` 里补，不用重读图。

### `unmapped` —— 过拟合的唯一信号

字段集是从看过的几页归纳出来的，必然过拟合。`unmapped` 是唯一能告诉我们
「这一页有东西装不下」的机制。

**实证**：前四页 `unmapped` 全 0，一度以为字段集稳了；第六轮跑剩下 7 页，
149 条里 33 条溢出，**28 条是划线原价**——因为前四页恰好都不印原价。

### 逃生口 —— 枚举必须留出口

封闭枚举的漏洞不是「填错」，是**静默填 null**：模型认出 `WILD CAUGHT` 是处理状态标签
（概念上挂上了 `freshness`），发现不在枚举里，于是写 `null`。它不会转投 `unmapped`，
因为 `unmapped` 说的是「没有字段认领」，而这个是「字段认领了但取值不合」。

所以每个枚举都要写成「常见 A / B / C **等等**」。

## 六、这些字段是怎么被用的

**这一节是字段存在的理由。写下来是因为下面这些决定之前只在对话里，
`netWeight` 就是这么丢了四个月的。**

### Bundle 三分法

```
① 没有 bundle      一件一件卖                 $1.39/LB · $2.99/EA
② 不可拆 bundle    几个单品绑成一份，只能整份买  12x12oz 一提啤酒 · 6/PK
                   → 藏在 sizes 的乘数里
③ 可拆 bundle      单品照卖，买够 N 件才有这个价  2 PACKS $10 · 3 FOR $9.99
                   → multibuy 字段
```

**单品 = 最小可买单位，不是最小物理个体。**

```
SUN GOLD KIWI  $24.99/CS  18S-22S/CS   一箱 18–22 个，但不能买一个 → 单品 = 箱
札幌啤酒        $11.99/PK  12x12oz      12 罐绑一起不能拆 → 单品 = 包
虾             $5.99      2 lb bag     16-20 ct 是等级不是 bundle → 单品 = 袋
```

### 算式链

```
单价 = (price ÷ multibuy) ÷ (pack_count × item_size)
```

四条验证：

```
黑豚绞肉   10.0 ÷ 2 ÷ (1 × 16oz)   = $5.00/lb
农心炸酱面  4.49 ÷ 1 ÷ (4 × 4.48oz) = $4.01/lb
札幌啤酒   11.99 ÷ 1 ÷ (12 × 12oz) = $1.33/lb
台湾啤酒    9.99 ÷ 1 ÷ (6 × 330ml) = $0.005/ml
```

### 加工层字段 —— 定义了，但一次都没跑过

**不在提示词里**（照抄层不做算术），由解析层从照抄字段推出：

| 字段 | 从哪来 | 说明 |
|---|---|---|
| `pack_count` | `sizes` 的乘数 | 一份里几个单品。`12x12oz` → 12；无乘数 → 1 |
| `item_size` | `sizes` | 一个单品含多少。`12x12oz` → 12 |
| `item_size_uom` | `sizes` | 单品的单位。`12x12oz` → `oz` |
| `norm_price` | 算式链 | 归一后的单价 |
| `norm_uom` | 归一表 | 只三个取值：`lb`（重量）`ml`（体积）`ea`（计数）|

**可解析性验过**：87 条真数据里 83 条能从 `sizes` 解析出 `pack_count` / `item_size`，
解析不了的 9 条全是「传单没印净重」（型号、尺寸、菇径分级、面包房现制品），
**没有一条是 bundle 判断不出来**。

### 身份键

```
生鲜   整条英文名 + freshness + size_grade
       两边都没等级时，算匹配（否则 88% 的生鲜永远配不上对）
```

**不拆商品名**：`JUMBO BLUEBERRIES (CLAMSHELL)` 里的 `JUMBO` 是等级、`CLAMSHELL` 是包装，
但它们印在名字里，抽出来需要判断 —— 留给解析层从 `name_en` 抽，不在读图层做。
判据是「印在哪里」不是「语义上属于什么」：印在名字之外的等级进 `size_grade`，
印在名字里的留在 `name_en`。

**条码是匹配键，不是身份键**：12pack 和 24pack 条码不同但归一后是同一件商品，
所以条码用来「把传单这条对上商品库那条」，不用来「认出这周和上周是同一件」。

## 八、已知硬伤（转录层，提示词压不住）

### 拿知识改传单上的字

```
SEABASS   传单印 鱈魚 → 模型写 鱸魚      **两轮稳定重现**
SHIRMP    传单拼错   → 模型改成 SHRIMP   间歇

```

`SEABASS` 那条尤其麻烦：智利海鲈在华人超市的中文名**就叫「鱈魚」**，
$29.99/LB 也对得上——**传单没印错，模型把对的改成了错的**。

提示词里「传单印错了也照抄」已经是最重的规则，压不住。

**`raw_text` 防不住这类错**——它记的是模型「读到的」，不是印着的。只有回原图才能发现。

### 漏读

```
YEOS 那格   传单印 10 个编码 + 6/PK  →  第 4 轮读到 8 个、没读到 6/PK
CICI 那格   传单印 8 个编码          →  读到 7 个
```

编码越密集越容易漏。

### 同页两次读不一致

第 4 轮 vs 第 5 轮同一页 26 条，**5 条有实质差异**，而且**互有对错**：
第 4 轮 4 胜、第 5 轮 1 胜，且第 5 轮唯一的胜利来自提示词修改，不是读得更好。

**转录质量随机波动，跟提示词质量不相关。**

**名字（中文名、英文名）都不能单独当身份键。**

### 一个可用的质检法

同一页跑两遍取差异：第 4/5 轮那次 5 条差异里 **4 条是真问题**（漏读、字段归错、

**但它抓不住系统性偏差**——`SEABASS` 两轮都错成一样。那类只能回原图。

## 九、解析层必须知道的坑

### 1. 原价和现价口径不同，直接比会得出「涨价」

```
PROROLL       原价 2.99/EA   现价 4.00   multibuy=2   "2 FOR $4.00"
99 RANCH 米饭  原价 1.69/EA   现价 5.00   multibuy=5   "5 FOR $5.00"
SMELT FISH    原价 6.99/PK   现价 8.88   multibuy=2   "2 PACKS $8.88"
```

**5 条实证。** `price` 是 bundle 总价、`original_price` 是单件价，
**两边都要先归一才能比**。

### 2. `multibuy` 只存数字，两种语义要靠 `conditions` 原文区分

```
"2 PACKS $8.88"  →  两包一共 $8.88，$4.44/包
"MUST BUY 2"     →  每包 $8.88，至少买两包
```

两者 `multibuy` 都是 2。**必须读 `conditions` 里的原文**才知道是哪种。
这就是「多件写法即使填了 `multibuy` 也要在 `conditions` 再抄一遍」的原因。

已核过 8 条：价签上的 `N FOR $X` / `N PACKS $X` **一律是总价**（8/8）。
`MUST BUY N` 是独立的红色标签，跟 `N FOR $X` **共存**，不是二选一。

### 3. 单位归一表必须建

```
PACKS / PK / pack        同一个概念
Ranch 商品库有 41 种写法：OZ 4682 · FOZ 740 · LB 389 · lb 106 · EA 332 · PC 76 …
归一后三个维度：重量 lb · 体积 ml · 计数 ea
```

**`FOZ`（液量盎司）不是 `OZ`（重量盎司）**，商品库里有 740 条（11%），
之前一直算错。

`ea` 是个杂类，里面混着卷、碗、条、盘（`bowl` `platter` `loaf` `roll`），
所以**比价必须先靠商品身份限定，不能只看单位相同**。

### 4. 有效期：接口不可信，11 页里 10 页跟接口不一致

```
p03  07.24 – 08.20        近一个月（Monthly Value Picks）
p02  08/14/26 – 08/16/26  3 天（Weekend Special，"Friday. Saturday. Sunday ONLY"）
p04  08.14 – 08.20        1 周
其余 08.07 – 08.20        2 周
p11  null                 纯广告页

接口对 11 页一律报 Aug.14 - Aug.20 —— 只有 p04 对上
```

**必须以图上印的为准。** 用接口的日期，周末特价会多卖四天、月度精选会少卖三周。

日期格式有 5 种写法（`08/07/26` `07.24` `08.14` `08.07.2026` `08.07`），**要归一**。

### 5. 纯广告页 `items=[]` 是正常状态

p11 Event Promotion 3 只有品牌标语（`99 RANCH SIGNATURE BRAND` /
`FROZEN AT PEAK FRESHNESS`），没有任何商品格。

**管线必须能区分「这一页本来就没商品」和「这一页抓取失败」**，否则对账天天报警。
